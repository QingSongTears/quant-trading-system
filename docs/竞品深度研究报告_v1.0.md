## 二、核心架构模式归纳

通过分析 10 个系统，提炼出 **4 种主流架构范式**：

### 范式 A：事件驱动架构 (Event-Driven)

```
行情事件 → 事件总线 → 策略引擎.next() → 信号 → 执行
```

| 代表 | 优点 | 缺点 |
|------|------|------|
| Zipline, VNPy, Backtrader | 贴近真实市场时序、易理解、实盘回测统一 | 逐bar循环，速度慢，难以大规模参数扫描 |

### 范式 B：向量化架构 (Vectorized)

```
全量数据矩阵 → 向量化运算 → 信号矩阵 → 统计聚合
```

| 代表 | 优点 | 缺点 |
|------|------|------|
| VectorBT, Backtesting.py | 极速（C级）、支持百万策略并行扫描、ML就绪 | 无法处理路径依赖逻辑，策略表达受限 |

### 范式 C：AI-Native 流水线

```
数据 → 因子工程 → 模型训练 → 预测信号 → 回测 → 组合优化
```

| 代表 | 优点 | 缺点 |
|------|------|------|
| Qlib, FinRL | 端到端AI集成、因子库/模型库开箱即用、AutoML | 学习曲线陡、黑盒风险、过拟合陷阱 |

### 范式 D：微服务分层架构

```
[数据服务] → [策略服务] → [回测服务] → [Web前端] → [执行网关]
     MongoDB / REST API / WebSocket / 多账户管理
```

| 代表 | 优点 | 缺点 |
|------|------|------|
| QUANTAXIS, VNPy | 模块解耦、可扩展、多用户、Web+桌面双端 | 架构重量级，小团队维护成本高 |

## 四、关键设计洞察

### 洞察 1：Qlib 的「因子即数据」理念

Qlib 最核心的设计创新是把因子计算从策略代码中分离出来：

```
传统方式：策略代码里嵌指标计算
Qlib方式：Alpha158 因子库 → 表达式引擎 → 因子DataFrame → 喂给任意模型
```

**对我们系统的启示**：当前 5 个预设策略各自内嵌指标计算。可以抽象一个「因子表达式引擎」，用户用 `Ref($close, -5) / Ref($close, -20) - 1` 这样的表达式定义因子，策略直接消费因子数据。

---

### 洞察 2：VectorBT 的「列即策略」模式

```
           fast=5    fast=10    fast=20
slow=20    [回测结果矩阵]      ← 一次运行，9种组合全部产出
slow=30
slow=40
```

**对我们系统的启示**：当前的参数网格搜索 (T16) 是串行 for 循环。可升级为向量化批量回测，一个矩阵运算产出所有参数组合的结果——速度提升 100x+。

---

### 洞察 3：VNPy 的「网关模式」

```
[策略引擎] → [网关抽象层] → [CTP网关] [XTP网关] [IB网关] ...
                   ↑
              统一接口，切换券商只需换网关
```

**对我们系统的启示**：当前数据层已有多源设计 (AKShare + WeStock + Baostock)，但回测引擎与 Backtesting.py 紧耦合。应抽象一个 `EngineGateway` 接口层，未来可平滑切换 VectorBT 或其他引擎。

---

### 洞察 4：FinRL 的「环境即市场」抽象

FinRL 把交易环境抽象为 OpenAI Gym 标准接口：

```python
env = StockTradingEnv(df, initial_capital=100000)
state = env.reset()
action = agent.predict(state)    # 0=hold, 1=buy, 2=sell
next_state, reward, done, _ = env.step(action)
```

**对我们系统的启示**：如果将回测引擎包装为 Gym 环境接口，就可以直接对接 DRL 模型（DQN/PPO/A2C）——零额外适配成本。

---

### 洞察 5：QUANTAXIS 的「数据中台」思想

QUANTAXIS 的最大设计特色是以 **MongoDB 为数据中台**，所有模块（行情/回测/实盘/Web）都通过 REST API 消费统一数据服务。

**对我们系统的启示**：当前 SQLite 单文件足够，但架构上应预留数据服务抽象层，未来扩展为独立数据服务时无需重写业务代码。

## 八、风险提示

| 风险 | 说明 | 缓解 |
|------|------|------|
| **过度设计** | 因子引擎/数据抽象层增加复杂度 | 每个 Phase 独立可交付，不强制全做 |
| **性能陷阱** | 向量化批量回测在大参数空间下内存暴涨 | 设置单次扫描上限 (≤10000组合) |
| **黑盒依赖** | LightGBM/RL 策略可解释性差 | 强制 SHAP 特征重要性 + 归因报告 |
| **维护成本** | 10个新模块代码量翻倍 | v2.0 完成后评估团队承载力再决定 v2.1 |

## 九、总结

经过对 10 个主流量化系统的深入研究，**我们的系统在数据处理、Web 可视化、策略对比方面已处于中上水平**。核心差距在于：

1. **因子体系缺失** — 所有高级策略（AI/ML/多因子）的基础
2. **回测性能天花板** — 串行参数扫描限制了策略优化的深度
3. **AI 策略能力为零** — 行业正在全面转向 AI-Native

建议**优先启动 v2.0（引擎升级）**，以最小的成本（2周）获得最大的性能提升和架构灵活性，为后续因子引擎和 AI 集成铺路。
